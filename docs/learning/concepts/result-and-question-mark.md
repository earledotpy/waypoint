# `Result` and `?`

## In one line

A Rust function that can fail returns a `Result`, which is *either* the value (`Ok(value)`) *or* the error (`Err(error)`), and `?` means "if this is an error, return it from my function now; otherwise give me the value".

## Where it appears here

- `crates/waypoint-domain/src/db.rs`, `open`, `open_in_memory` and `prepare`: each returns `Result<Connection, DomainError>` and uses `?` after every call that can fail.
- `crates/waypoint-domain/src/error.rs`, `DomainError`: the one error type the domain returns, and the two `impl From<…>` blocks that let `?` convert library errors into it.
- `crates/waypoint-domain/src/node.rs`, `create_node`: returns `Err(DomainError::EmptyTitle)` itself for a blank title, and uses `?` on the `INSERT`.
- `crates/waypoint-read/src/node.rs`, `list_nodes`: returns `rusqlite::Result<Vec<SkillNode>>`, not a `DomainError` (see "Two error types" below).

## What it does

`Result<T, E>` is an enum with two variants. A function returning `Result<Connection, DomainError>` hands back either `Ok(conn)` or `Err(some_domain_error)`, never both and never neither. The caller can't use the `Connection` without first dealing with the possibility that it's an error.

Dealing with it in full looks like this:

```rust
let conn = match Connection::open(path) {
    Ok(conn) => conn,
    Err(e) => return Err(DomainError::from(e)),
};
```

`?` is short for exactly that. This line in `open` does the same thing:

```rust
let conn = Connection::open(path)?;
```

Note the `DomainError::from(e)`. `Connection::open` fails with a `rusqlite::Error`, but `open` promises to return a `DomainError`. `?` bridges the two by calling `From`: it looks for an `impl From<rusqlite::Error> for DomainError`. `error.rs` provides that impl, and it wraps the library error in the `Database` variant. The same happens in `prepare`, where `migrations().to_latest(&mut conn)?` fails with a `rusqlite_migration::Error` and `?` uses the second `From` impl to wrap it in `Migration`. If no matching `From` exists, the code doesn't compile.

`Ok(conn)` at the end of `prepare` is the success case, written out.

### Two error types: `DomainError` and `rusqlite::Result`

`create_node` returns `Result<SkillNode, DomainError>`, but `list_nodes` returns `rusqlite::Result<Vec<SkillNode>>`, which is short for `Result<Vec<SkillNode>, rusqlite::Error>`. The difference comes from where each function lives. `list_nodes` is in `waypoint-read`, which may not depend on `waypoint-domain` ([ADR 0001](../../adr/0001-crate-layout-write-hiding-and-frontend-tooling.md) §2), so it can't even name `DomainError`. That's fine, because a read can only fail one way: SQLite refused. `create_node` can also fail by Waypoint's own rules, like `EmptyTitle`, and those failures need a variant of their own. The two fit together through `?`: domain code that calls `list_nodes(conn)?` gets its `rusqlite::Error` wrapped in `DomainError::Database` by the same `From` impl as any other SQLite call.

## Python comparison

The nearest Python idea is exceptions, with `raise … from`:

```python
class DomainError(Exception): ...

def open_db(path):
    try:
        conn = sqlite3.connect(path)
    except sqlite3.Error as e:
        raise DomainError("database error") from e
    return conn
```

`?` is the `except … raise DomainError from e` part, done in one character, and `DomainError`'s `source()` (in `error.rs`) plays the role of `__cause__`: the original error stays attached.

Where the analogy breaks: in Python the possible failure is invisible in `open_db`'s signature. A caller can forget the `try`, and the exception flies up until something catches it, or crashes the program. In Rust the failure *is* the return type. `open` says `-> Result<Connection, DomainError>`, so a caller that ignores the error doesn't get a `Connection` at all, and the compiler warns about a `Result` that's never looked at. Nothing is thrown, and nothing unwinds through the caller: `?` is an ordinary, early `return`. Every place a function can fail is marked with a visible `?`.

(Rust does have a crash-the-program mechanism, `panic!`, and `.unwrap()` triggers it on an `Err`. The tests in `db.rs` use `.unwrap()` on purpose, because a test *should* stop at the first thing that goes wrong. App code returns `Result` instead.)

## Why this code uses it

Opening a database can fail for ordinary reasons: the folder doesn't exist, the file is locked, a migration's SQL is wrong. Those failures have to reach the app, and eventually the learner, as a message rather than a crash. `Result` makes every caller handle them, and `DomainError` gives the app one type to handle, whichever library failed underneath.

The `From` impls and `Display` are written by hand rather than generated by the `thiserror` crate, per `AGENTS.md` ("Plain construction"), so every line of the conversion is visible.
