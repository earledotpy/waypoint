# Traits and `impl` blocks

## In one line

A trait is a named set of methods a type can promise to have, and `impl SomeTrait for SomeType { … }` is where the type keeps that promise.

## Where it appears here

- `crates/waypoint-domain/src/error.rs`, `DomainError`: four `impl` blocks:
  - `fmt::Display`, the human-readable message
  - `std::error::Error`, which marks it as an error and gives `source`
  - `From<rusqlite::Error>` and `From<rusqlite_migration::Error>`, which let `?` convert library errors
- The same file, `#[derive(Debug)]`: asks the compiler to *write* the `Debug` impl for us.

## What it does

A trait lists method signatures. `Display`, from the standard library, has one:

```rust
fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result;
```

`impl fmt::Display for DomainError { fn fmt(…) { … } }` supplies that method for `DomainError`. From then on, anything written to work with "any type that implements `Display`" works with `DomainError` too: `format!("{e}")`, `e.to_string()`, `println!("{e}")`. The compiler checks the promise. Leave out `fmt`, or give it the wrong signature, and the `impl` doesn't compile.

The same pattern gives `DomainError` its other abilities:

- **`From<rusqlite::Error>`** has one method, `from`, which turns a `rusqlite::Error` into a `DomainError`. `?` looks for exactly this impl (see [`Result` and `?`](result-and-question-mark.md)).
- **`std::error::Error`** requires `Display` and `Debug` to exist already, and adds an optional `source` method. `dyn std::error::Error` in `source`'s return type means "a value of *some* type that implements `Error`". The caller doesn't need to know which one.
- **`#[derive(Debug)]`** is the shortcut: for a few standard traits, the compiler can write the impl from the type's shape. `Debug` is the developer-facing print (`{e:?}`), used by `.unwrap()` when it panics.

An `impl` block with no trait (`impl DomainError { fn … }`) also exists. It adds ordinary methods to one type. Waypoint has none yet.

## Python comparison

The nearest Python ideas are **dunder methods** and **`typing.Protocol`**. `impl Display` is like writing `__str__`, and `print(e)` calls it. A trait as a whole is like a `Protocol`: "anything with these methods counts".

Where the analogy breaks:

- **It's checked when compiling, not at runtime.** Python finds out that `__str__` is missing, or misspelled, only when something calls it. Rust refuses to build.
- **Opt-in by name.** A Python `Protocol` matches any class that happens to have the right methods ("duck typing"). A Rust type implements a trait only if someone writes `impl Trait for Type`.
- **The impl can live apart from the type.** In Python, `__str__` must be inside the `class` body. In Rust, `impl` blocks can go anywhere in the crate, and you can implement a trait from another crate (`Display`, from `std`) for your own type. The rule is that the trait or the type must be yours.
- **No inheritance of data.** A trait carries methods, never fields. There's no `class DomainError(Exception)` subclassing. `DomainError` *is* an error because it implements `Error`, not because it inherits from it.

## Why this code uses it

The rest of Rust talks to errors through traits. `?` needs `From`, and printing needs `Display`. Tauri, when the app returns the error to the UI, needs it too. Implementing those traits is how `DomainError` plugs into all of that. They're written out by hand, not generated by `thiserror`, so each one is visible (`AGENTS.md`, "Plain construction").
